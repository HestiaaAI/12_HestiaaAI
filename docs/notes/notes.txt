Section 2 — four view implementations (September 20, 2026)

Demo (populated database): http://127.0.0.1:8001/tasks/cbv-generic/

All four routes read Task rows, search titles through the GET parameter q, and
render the same tasks/task_list.html. Only the implementation changes, so identical
output is expected. Creating and assigning work comes later: Task is the reusable
definition, dates live on TaskOccurrence and responses on Assignment.

  A01  task_manual_view  /tasks/manual/       Manual FBV: loader.get_template, then HttpResponse    http://127.0.0.1:8000/tasks/manual/
  A02  task_render_view  /tasks/render/       FBV using the render() shortcut                       http://127.0.0.1:8000/tasks/render/
  A03  TaskBaseView      /tasks/cbv-base/     CBV inheriting View, explicit get()                   http://127.0.0.1:8000/tasks/cbv-base/
  A04  TaskListView      /tasks/cbv-generic/  CBV inheriting ListView, search in get_queryset()     http://127.0.0.1:8000/tasks/cbv-generic/

URL names are workflows:task-manual, task-render, task-cbv-base, task-cbv-generic.


What I found useful, and when

HttpResponse vs render
Writing task_manual_view first was worth doing once. Loading the template,
rendering it to a string and wrapping that in HttpResponse shows the three steps,
and made clear that render() returns the same HttpResponse rather than a different
kind of thing. After that I used render() everywhere here, since every response is
a full HTML page and the manual version only adds lines.

HttpResponse earns its place when there is no template. The receipt upload flow
will need JSON for fetch calls, a status code on a rejected duplicate, and a file
download. Those are HttpResponse or JsonResponse, not render.

Base CBV vs Generic CBV
TaskBaseView made the GET path explicit: I wrote get() myself, queried Task and
called render. More code than the generic version for the same page, but nothing
hidden, which helped while I was still confirming the URL names resolved to the
classes I expected.

TaskListView removed most of that. Declaring model, template_name and
context_object_name covered the list flow, and only get_queryset() needed
overriding for the search. The rule I settled on: when a view is exactly "query a
model, filter, render a list", ListView already does it; when it is not, the base
View is easier than fighting the generic one.

The trade-off showed up in something small. The view_style label was one dict key
in the base view's get(), but needed extra_context on ListView. Accepting or
declining an assignment is a POST that changes state with no matching generic
view, so that will be a base View or a form view.

Reproducing the demo

From the project root, using the .venv environment described in README.md. Creates
a temporary SQLite database and never touches the project's db.sqlite3. Ctrl-C to
stop. For the empty-database capture, run again in a second terminal with
HESTIA_DEMO_MODE=empty, which serves on port 8002.

```bash
HESTIA_DEMO_MODE=populated .venv/bin/python - <<'PYDEMO'
import os
import tempfile
from pathlib import Path

mode = os.environ["HESTIA_DEMO_MODE"]
assert mode in {"populated", "empty"}
os.environ["DJANGO_SETTINGS_MODULE"] = "hestia_config.settings.development"
from django.conf import settings
settings.DATABASES = {"default": {
    "ENGINE": "django.db.backends.sqlite3",
    "NAME": Path(tempfile.mkdtemp(prefix="hestia-demo-")) / "db.sqlite3",
}}
import django
django.setup()
from django.core.management import call_command
call_command("migrate", interactive=False, verbosity=0)
if mode == "populated":
    call_command("seed_template_demo")
port = "8001" if mode == "populated" else "8002"
call_command("runserver", "127.0.0.1:" + port, use_reloader=False)
PYDEMO
```
