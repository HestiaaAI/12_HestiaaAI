Comparison notes — why each style is useful here
------------------------------------------------
HttpResponse vs render():
The manual view makes the request-to-template-to-response steps visible,
which is useful for understanding Django and for responses needing explicit
control. It requires more plumbing for this ordinary HTML list. render()
expresses the same query/context/template flow more concisely, making it a
useful default for a small custom page.

Base CBV vs generic CBV:
TaskBaseView makes get() and its query explicit. This style is useful when
request handling has custom steps or different GET/POST behavior.
TaskListView is the shortest fit for a conventional model list: Django
provides the list context and rendering behavior, while get_queryset()
provides a focused extension point for title filtering.

Template separation:
Keeping identical tasks context and one list template means changing a card
or empty-state message fixes the output of all four view styles. The choice
of view style does not require duplicating presentation code.

URL linking, navigation, and static files
==================================
Home page
The project needs a real page at /. HomePageView in hestia_config/views.py
is mapped from hestia_config/urls.py with name="home" and renders
templates/home.html. Without this route, the browser shows Django's 404
at the site root.

Navigation
templates/base.html uses named {% url %} tags so paths are not hard-coded.
The bar links Home ({% url 'home' %}), Household tasks
({% url 'workflows:task-cbv-generic' %}), Task board
({% url 'task_forms:board' %}), Search tasks ({% url 'task_search:get' %}),
Task statistics ({% url 'analytics:task-stats' %}), and Sign in
({% url 'accounts:login' %}).
Named URLs stay correct if a path later changes.

Why get_absolute_url() is useful
Task.get_absolute_url() reverses workflows:task-detail with the task
primary key. The same Task object is shown on several list pages and the
Task board. Templates use {{ task.get_absolute_url }} instead of writing
/tasks/{{ task.pk }}/ in each place. If the detail route later moves, only
the model method needs to change. The list template uses this for the
title and "View details" links.

Model → URL → view → template
Task → workflows/urls.py path "<int:pk>/" (name=task-detail) →
TaskDetailView → templates/tasks/task_detail.html. Home follows the same
pattern: hestia_config/urls.py → HomePageView → templates/home.html.

Task board route
The board lives at /tasks/manage/ through include("workflows.forms_urls")
in the shared root URLconf so the nav link and login redirect resolve.

Static file organization
STATICFILES_DIRS points at the project-level "static files/" folder so
shared CSS (css/style.css), board CSS (css/hestia.css), and
images/hestia-mark.svg stay in one place. Templates load them with
{% load static %}. Project-level static files are used because the header,
nav, and cards are shared across apps, not owned by a single app.

Cache busting
base.html loads {% static 'css/style.css' %}?v={{ ts }} where ts is
{% now "U" %}. The changing Unix timestamp gives the stylesheet a new URL
after a refresh so the browser does not keep a stale copy while you edit
CSS. hestia.css uses a manual version suffix (?v=20260926-1) that should
be incremented when that file changes.

TaskBoardView uses a validated GET filter form and a POST Task ModelForm.
The assignment board is public: no sign-in is required to filter or create
tasks. Anonymous creates leave creator empty; signed-in users get creator
attribution only for a matching active membership. POST includes CSRF
protection and uses POST/Redirect/GET; errors retain user input. Shared
static assets remain in the existing project-level static files/ directory.
The version suffix on hestia.css provides cache busting. The feature extends
base.html through its existing blocks. The root URL is
path("tasks/manage/", include("workflows.forms_urls")) and the nav uses
{% url 'task_forms:board' %}.

Search and API (Person 2)
==================
Routes
hestia_config/urls.py mounts path("tasks/search/", include(
"workflows.search_urls")) and path("api/", include("api.urls")) above the
tasks/ includes, so no tasks/ route can catch /tasks/search/ first.
  /tasks/search/          task_search:get     GET search
  /tasks/search/post/     task_search:post    POST search
  /api/tasks/             api:task-list       JSON list (JsonResponse)
  /api/response-demo/     api:response-demo   plain text (HttpResponse)

GET search vs POST search
Both forms read the same two fields: q (task title) and workspace_name
(household name). The GET view reads request.GET, so the terms appear in the
URL and a search can be bookmarked or shared. The POST view reads
request.POST, so the terms travel in the request body and the address bar
stays at /tasks/search/post/. The POST form includes {% csrf_token %}; a
POST without a token is rejected with 403. POST only changes where the
terms travel. It does not encrypt them or add access control. The POST
search is read-only: it never creates a Task and renders results directly.

Relationship-spanning query
workflows/task_queries.py filter_task_queryset() uses title__icontains for
the title and workspace__name__icontains for the household. The double
underscore follows the Task.workspace foreign key to Workspace.name, so
Django adds the JOIN. When both terms are given, both must match. Blank
terms are ignored. Results are ordered by task_id so tests are
deterministic.

Results template
templates/tasks/search.html extends base.html and renders results with
{% for task in tasks %} / {% empty %}. The empty clause shows
"No tasks match" and repeats the escaped search terms. Each title links
through {{ task.get_absolute_url }} to the detail page.

API design and data served
/api/tasks/ is GET-only. It accepts the same q and workspace_name query
parameters, for example /api/tasks/?q=groceries&workspace_name=demo, and
returns {"tasks": [{"id", "title", "task_type", "priority"}]}. id is the
Task primary key; task_type and priority are raw choice values. An
unmatched search returns {"tasks": []}. Descriptions, locations, documents
and membership details are never included. Like the other teaching pages
the API is public, so use it only with fictional demo data.

HttpResponse vs JsonResponse
HttpResponse sends whatever content and MIME type the view gives it:
/api/response-demo/ returns "Hestia task API" with Content-Type text/plain.
JsonResponse takes a Python dict, serializes it to JSON and sets
Content-Type: application/json, so the view never builds JSON text by hand.

Part 3 — Cost & Scaling (Person 2)
----------------------------------
At ~10,000 DAU × 2 dumps/user ≈ 20,000 extractions/day (~12M tokens/day if
~600 tokens/request):

| Approach | Cost driver | At 10k DAU |
| --- | --- | --- |
| Local Django HF (1–3B instruct) | Always-on CPU/GPU nodes | Expensive idle + hard concurrency |
| Hosted API | Per-token | Scales with usage; simpler ops |
| Hybrid | Local extract + API for complex plans | Best balance with Person 3 |

Stay local for class demos / low traffic. Prefer API or hybrid at 10k DAU:
interactive latency for TinyLlama/Qwen-class models needs many replicas on CPU.
A fixed 16-core CPU / GPU / 64 GB box is acceptable when traffic is steady and
data locality matters; switch to a paid API when traffic is spiky or idle GPU
cost exceeds token spend.

Part 3 — Local pre-trained model vs paid API (P4)
------------------------------------------------
Full examples/tables/sources: docs/a6-person-4/local-vs-api.md.
At 10,000 DAU x two extractions/day, assume 800 input + 220 output tokens/request.
Groq GPT-OSS 20B ($0.075/M input, $0.30/M output, checked Oct 18) gives $2.52/day,
$75.60/30 days. A published Runpod RTX 3090 example at $0.50/hour is $360/30 days
before extra costs; this is not a quote for the hypothetical exact server.
At the same assumed token usage, billing-only break-even is ~95,238 requests/day;
capacity and quality must be measured separately. GPU VRAM matters more than a
"16-core GPU" label. A 14B FP16 model needs ~28GB weights before KV/runtime memory.
Use owned/local capacity for low traffic, privacy or predictable utilization;
use API when burst scaling and rental economics favor per-token billing.
Hybrid extraction + explicit external breakdown is supported in P4's review UI,
but Person 3 still owns the provider. Hybrid is not automatically cheaper if it
requires an otherwise-unneeded dedicated GPU. No paid API experiment is claimed.

P4 hypothetical server decision — 16 CPU cores, 64GB RAM, 1TB disk, GPU unspecified
| Condition | Prefer local | Prefer paid API |
| Hardware already owned | Low marginal cost can favor local | Compare maintenance/energy too |
| New always-on GPU rental | Needs enough steady utilization | Low/spiky demand avoids idle rental |
| Household data locality | Keep processing on controlled machine | Requires acceptable privacy terms |
| Higher-quality model needed | Benchmark upgrade and hardware fit | Can access larger models on demand |
| Burst traffic | Queue/batch with bounded latency | Provision rate limits and quotas |
| Model memory | Check GPU VRAM + KV/runtime overhead | Provider manages model hosting |

Approximate weights before KV/runtime/OS overhead:
| Model size | FP32 | FP16/BF16 | 4-bit, before metadata |
| 0.5B | 2GB | 1GB | 0.25GB |
| 7B | 28GB | 14GB | 3.5GB |
| 14B | 56GB | 28GB | 7GB |
A 24GB GPU cannot hold unquantized 14B FP16 weights even when host RAM is 64GB.
Quantization support/quality must be separately tested. Disk space is not VRAM.
"16-core GPU" is insufficient hardware information; specify device/VRAM/bandwidth.

At 20,000 requests/day, mean arrivals are 0.2315 requests/second. For measured
local generation latency L seconds, a serialized architecture needs at least
0.2315 x L busy workers before peaks, prompt work and headroom. A 5x peak needs
five times that service capacity. Billing break-even does not prove throughput.

Hybrid example: external extraction for 20% of 20,000 requests costs $0.504/day.
External breakdowns for 10%, at 300 input/600 output tokens, cost $0.405/day.
Together $27.27/month plus local hosting; $387.27 with a new $360 GPU rental.
All-API extraction plus the same breakdown volume is $87.75/month, so this hybrid
is not automatically cheaper. Owned hardware or stricter data locality can alter
the choice. User-requested breakdown is disclosed and reviewed before saving;
malformed schemas do not provide a calibrated semantic confidence score.

https://console.groq.com/docs/models
https://www.runpod.io/pricing
Costs exclude app hosting, storage/network, retries, engineering and taxes.
No exact quote for the hypothetical 16-core/64GB/1TB server is claimed.

A6 - Person 3: Hybrid Potential (October 18, 2026)
================================================
Feature implemented on dev-ddhene2-a6-external-ai:
  POST /api/tasks/<pk>/action-plan/ and GET/POST /tasks/<pk>/action-plan/.
  Groq openai/gpt-oss-20b produces a validated draft action plan for one saved
  Task. The endpoint uses the signed-in user's active workspace membership.
  A real local fictional-task request succeeded; see
  docs/a6-person-3/evidence/groq-smoke.json. This is not production evidence.

How the local Hugging Face model and external API can work together
-----------------------------------------------------------------
The proposed complete team pipeline is:
  1. P2's local model converts a Brain Dump into title/type/priority/description.
  2. P4's UI lets the user edit, remove, confirm and save the extracted Tasks.
  3. For a selected complex SAVED task, the user explicitly requests a Groq plan.
  4. Only that task's four fields are transmitted, then the validated draft is
     shown for review. No automatic write or subtask creation occurs in P3.

The local extractor handles the frequent, short, well-defined extraction task.
The hosted model handles occasional multi-step planning. The split avoids paying
to send every simple task to the cloud and avoids loading a large planning model
inside each Django worker. P3 does not import torch or load HF weights on requests.
P2's actual extraction quality, latency and selected model remain P2/P1 evidence;
P3 does not invent benchmark conclusions for the four assigned models.

Routing examples (proposed full-team behavior)
| User concern                         | Local/human path                  | Groq path                         |
|--------------------------------------|-----------------------------------|-----------------------------------|
| Buy milk; take out trash              | Extract/edit/save two tasks       | None needed                       |
| Prepare guest room before Friday     | Save one reviewed task            | On click, cleaning/bedding steps  |
| Organize household move               | Extract major responsibilities    | Plan one selected responsibility  |
| Ambiguous or malformed local output   | Reject/ask user to edit or clarify | Only with explicit user consent   |
| Possible gas leak                     | Flag urgent review/safe help      | Never treat AI as emergency care  |

Structured JSON is not proof of correctness. Validate enum choices, field types,
lengths and number of tasks locally; use human corrections to detect missed or
invented concerns. Do not use a made-up model confidence threshold as a substitute
for evaluation. A cloud fallback for failed extraction could be added later, but
it must be labeled and explicitly authorized; it is not silently enabled here.

Worked cost example (estimate, not measured usage)
------------------------------------------------
Let N be daily requests for planning, Tin/Tout be mean input/output tokens, and
Pin/Pout be dollars per million tokens:
  API dollars/day = N * (Tin * Pin + Tout * Pout) / 1,000,000.
Groq's published model table checked October 18, 2026 lists gpt-oss-20b at
$0.075 input / $0.30 output per million tokens. Assume 10,000 daily interactions,
400 input + 600 output BILLABLE tokens per external call and a 30-day month.

| Routing approach              | External calls/day | API $/day | API $/30 days |
|-------------------------------|-------------------:|----------:|--------------:|
| Send every interaction        |             10,000 |      2.10 |         63.00 |
| Local first, 20% ask for plans |              2,000 |      0.42 |         12.60 |
| Local first, 10% ask for plans |              1,000 |      0.21 |          6.30 |

At a 10% routing rate, API usage is 90% lower than the all-cloud example, but the
local hardware, electricity, operations and development costs are additional.
Include billed reasoning tokens in Tout when applicable; a visible 600-token
answer can cost more if hidden reasoning is also billed. The request cap here is
2,048 completion tokens, not a promise that every call consumes 600. Measure the
provider's usage counters and revise estimates. Free-tier quotas and price/model
availability can change; do not assume a free tier serves 10,000 daily users.

The hybrid approach is financially preferable to all-cloud only if:
  incremental local cost/month < avoided API cost/month,
at comparable quality and acceptable latency. In the 10% example the avoided
API expense is $56.70/month. Renting a new GPU for extraction could exceed that
saving; reusing existing adequately sized hardware might not. If local extraction
causes many corrections, lost user time is another cost. Benchmark before choosing.

Quality and privacy controls in P3
---------------------------------
- User clicks a button disclosing that Groq receives task details. GET is free of
  provider calls. Only active members can send their household's task data.
- Send title/type/priority/description only. Do not include workspace names,
  membership records, uploaded documents, login information or the full Brain Dump.
- Requests use a fixed HTTPS host, no redirects, connect/read timeouts, and no
  automatic retries that could duplicate costs. Keys stay in ignored .env files.
- Exact JSON fields/types/limits are checked. Invalid, refused or truncated
  responses are discarded; external errors never expose provider bodies or keys.
- Output is escaped, never interpreted as code, and never saved automatically.
- A 15-second per-user cache cooldown limits repeat clicks. The default local
  cache is per worker; production needs a shared cache/provider budget controls
  for stronger quota enforcement. No plan is cached or logged by this feature.
- Keep external processing optional. Users can edit tasks manually if the API is
  unavailable or if they prefer not to transmit task descriptions to a provider.
