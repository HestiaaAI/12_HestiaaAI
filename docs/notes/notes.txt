Section 2
================================
Selected domain model: workflows.models.Task.
Paths are relative to the local development server (http://127.0.0.1:8000).
All four views are in workflows/views.py; their named routes are in
workflows/urls.py and are included under /tasks/ by hestia_config/urls.py.

1. HttpResponse function-based view (manual)
   Name: task_manual_view
   URL: /tasks/manual/
   Route name: workflows:task-manual
   Purpose: list household task definitions, optionally filtered by title.
   Implementation: query Task; load tasks/task_list.html with
   loader.get_template(); render a context containing tasks; wrap the HTML
   in HttpResponse.
   Screenshot: docs/screenshots/01-httpresponse-fbv.png

2. render() function-based view (shortcut)
   Name: task_render_view
   URL: /tasks/render/
   Route name: workflows:task-render
   Purpose: display the same task list through Django's render shortcut.
   Implementation: query Task, supply {"tasks": tasks}, and return
   render(request, "tasks/task_list.html", context).
   Screenshot: docs/screenshots/02-render-fbv.png

3. Base class-based view
   Name: TaskBaseView
   URL: /tasks/cbv-base/
   Route name: workflows:task-cbv-base
   Purpose: demonstrate explicit request handling in a View subclass.
   Implementation: inherits django.views.View, implements get(), manually
   queries Task and renders the shared template with context.
   Screenshot: docs/screenshots/03-base-cbv.png

4. Generic class-based view
   Name: TaskListView
   URL: /tasks/cbv-generic/
   Route name: workflows:task-cbv-generic
   Purpose: display tasks using Django's built-in list-view behavior.
   Implementation: inherits ListView; model = Task;
   template_name = "tasks/task_list.html"; context_object_name = "tasks".
   get_queryset() applies the same optional title filter as the other views.
   Screenshot: docs/screenshots/04-generic-cbv.png

Comparison notes — why each style is useful here
------------------------------------------------
HttpResponse vs render():
The manual view makes the request-to-template-to-response steps visible,
which is useful for understanding Django and for responses needing explicit
control. It requires more plumbing for this ordinary HTML list. render()
expresses the same query/context/template flow more concisely, making it a
useful default for a small custom page.

Base CBV vs generic CBV:
TaskBaseView makes get() and its query explicit. This style is useful when
request handling has custom steps or different GET/POST behavior.
TaskListView is the shortest fit for a conventional model list: Django
provides the list context and rendering behavior, while get_queryset()
provides a focused extension point for title filtering.

Template separation:
Keeping identical tasks context and one list template means changing a card
or empty-state message fixes the output of all four view styles. The choice
of view style does not require duplicating presentation code.
